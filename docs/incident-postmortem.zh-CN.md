# 事故复盘：hive 重排两次毁掉启动菜单

**机器：** Firebat GM6BG5Q-F 笔记本，Windows 11 26100，UEFI + VBS
**影响：** 2 次引导失败，需要 Linux 侧恢复；无数据损失
**作者：** 依据会话日志重建，2026-11-15

> English version: [incident-postmortem.md](incident-postmortem.md)

## 时间线

### 第一次尝试 — hivex 结构编辑
* 目标：删除两个陈旧 BCD 条目，重写 bootmgr `displayorder`。
* 工具：python-hivex `node_delete_child` + `node_set_value` + `commit()`。
* 内容验证通过（hivex 重解析显示预期状态）。
* **结果：bootmgr 拒收该 hive。无菜单，"Please wait" → 崩溃。**
* 恢复：原始备份拷回；机器恢复引导。

### 第二次尝试 — chntpw 删除 + hivex 值写入
* 目标：同一改动，当时以为第一次的失败原因是 LOG 失配。
* chntpw `rdel` 删除对象（格式忠实），displayorder 值仍用 hivex
  `commit()` 写入；这次隔离了 LOG。
* 内容验证再次通过。
* **结果：完全相同的失败。**

## 根因分析

对已知可引导 hive 与被拒 hive 做二进制取证对比：

| 区域 | 结论 |
|---|---|
| 基块 | 仅合法差异（seq++、binsize 多一页、校验和自洽） |
| hbin 链 | 30 页，全部 `hbin`，相对偏移正确 |
| nk/vk/索引记录 | 全部可解析，计数与删除的 2 棵子树一致 |
| 头部校验和 | hivex 正确重算 |

所有能离线执行的检查全部通过。**这个 hive 在一切可用的度量下都是结构合法的，
bootmgr 照样拒收。** 剩余的差异藏在 hivex 的重排实现内部（单元格布局、分配
粒度、或某种 hivex 未复现的 regf 次版本细节）。我们无法完全刻画它——而这正是
要点所在：**当你无法刻画 bootmgr 接受什么时，就不要重新生成容器——只补丁最少
的字节。**

## 修复：字节受限补丁

同一语义改动，改为在 `displayorder` 值数据内做就地同长度字节替换：

* 总共只改 2 个字节（GUID 数字 `'90'→'92'`、`'91'→'92'`）
* 文件长度、头部、hbin、校验和、序列号：全部未动
* 差异可验证地局限于两个补丁范围之内

这**从构造上**消灭了整个失败类别：如果原件能引导，补丁副本就能引导
（只有值载荷字节不同，且载荷语义被选为引用已存在的条目）。

## 本仓库沉淀的教训

1. 内容级验证（哪怕是 hivex 重解析）**不等于** Windows 接受重排后的 hive。
2. LOG 隔离是必要条件，但不是充分条件。
3. `chntpw` 的静默写失败（RO 回退只打印一行）必须通过重读文件来确认，
   不能相信它的 "OK"。
4. GUID 大小写在对象键与 displayorder 列表之间不一致——大小写敏感的
   成员检查会产生错误的 "MISSING" 诊断（代价：一次错误的取证结论）。
5. 启动菜单就是 displayorder。在其中的语义改动是安全子集；结构性对象删除
   是危险子集。优先选择指针替换。
